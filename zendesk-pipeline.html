the zendesk support pipeline

375ai · october 2025 to july 2026 · zendesk, zapier, linear

story

In October 2025 we publicly launched 375go, our mobile app. It passed 250,000 downloads worldwide, and with that came a wave of support requests: crashes, login problems, missing rewards, questions about how the app worked.

The team had no channel to organize, understand and resolve those requests. I set up and administered Zendesk for the company, and I answered the support tickets myself. One inbox, one person. I needed a way to handle the volume without answering every ticket by hand.

how it works

I built the pipeline around Zendesk's own AI agent. It answers from our knowledge base using retrieval-augmented generation, so every reply comes from a document we wrote, not from a guess. I wrote the knowledge base, configured the agent, and designed the status flow that moves a ticket from a machine to a person to an engineer.

Three tools carry the work.

The knowledge base started with what we already had: FAQs, technical documentation, support articles, and how-to guides with documented steps for common issues. No answer was added without a source document behind it.

Every inquiry got the same first pass. The agent greeted the user, assessed the message, and replied with specific steps for the user's issue. If the issue survived that first reply, the agent asked for what an engineer would eventually need: device details, steps to reproduce, screenshots, videos. All of it went onto the ticket.

A ticket changed hands on one condition: the agent had no clear path forward. Guesswork was not allowed, so the status moved to needs human and I joined the conversation.

I reviewed the ticket, asked for anything still missing, and set the status to eng review. Zapier watched for that status, pulled the ticket data, and created a Linear ticket with everything engineering needed: the user and device info, a description of the issue, the steps already tried, and the steps to reproduce it.

impact

In the first six months, more than 1,000 common issues were resolved by the agent with no human in the loop. Our community described support as diligent and helpful.

The pipeline saved me an estimated 20 to 25 hours of work every week. Tickets stopped piling up while I answered them one at a time.

what i learned

The bottleneck was me. I was the only path between the engineering team and the end users, and the limit was seats. We were on a starter plan with a single seat, so the engineers had no way to open a ticket. In a perfect world I would have given two to four engineers direct access.

The cheap version of a fix is a relay. Suggestions from engineering arrive at my email with the ticket identifier, and an agent posts the reply to the user through the Zendesk interface while logged in as me. That is duct tape, and it still leans on my account.

The more honest version keeps the same relay and moves the payload. Engineering sends the reply as an API or MCP request, a relay layer checks the ticket, and the Zendesk API posts it. No computer-use loop, no borrowed login. I have not shipped that version, and I would not claim it works until I tested it against the seat model.

What I would test first: whether an API integration can post an agent reply on a plan where the engineers have no seats. If it can, the human stops being the relay and goes back to being the reviewer.
